# 构建本地 HTML 人工审核工作流

## 目标

将“程序处理 + 人工复核 + 结果展示”实现为可审计的本地闭环：

```text
输入文件 → 自动处理 → 正式结构化数据 → HTML 展示
                         ↓
                    待审核数据 → 人工决定
                         ↓
              校验并回写正式数据 → 重新生成 HTML
```

优先使用项目已有语言和技术栈。除非现有前端复杂度确有需要，否则采用静态
HTML/CSS/JavaScript 加轻量 localhost 服务，避免引入不必要的前端构建链。

## 先判断是否适合替代 Excel

在编码前确认主要需求。

选择本地 HTML：

- 人工主要进行查阅、筛选、比对、确认、排除和少量结构化填报。
- 需要展示大量文档链接、图片、状态、匹配依据或 AI/OCR 结果。
- 需要固定交互、输入校验、审核版本控制和操作日志。
- 需要适配特定屏幕、控制列宽、分组、颜色和交互菜单。
- 数据必须由程序统一生成和回写，不能依赖人工随意修改表格结构。

保留 Excel 或仅增加 HTML 辅助页：

- 核心工作是自由制表、公式计算、透视分析或大批量单元格编辑。
- 用户必须离线交换一个可编辑工作簿。
- 现有组织流程把签章、宏或工作簿格式作为正式成果。

改用正式 Web 应用而不是轻量 localhost 服务：

- 多名用户需要同时审核同一批数据。
- 需要远程访问、账号权限、集中部署或实时协作。
- 审核决定必须由服务端数据库事务统一处理。

不要为了“界面更好看”而复制两套可编辑事实数据。确需 Excel 导出时，将其
定义为只读交换成果，并始终从正式数据重新生成。

## 核心不变量

实施过程中始终保持以下约束：

1. 只设一个正式事实数据源。优先使用 JSON、数据库或现有结构化存储。
2. HTML 只作为投影视图和交互客户端，不作为正式数据输入。
3. 审核决定必须经过本地服务校验后回写；不要让浏览器直接覆盖正式文件。
4. 数据变更后重新生成所有派生页面，禁止手工维护 HTML 内容。
5. 文件路径保存为相对资料根目录的路径；服务端解析后必须验证仍在根目录内。
6. 文件移动、重新分类、审核确认、排除和恢复均写入审计记录。
7. 删除操作默认改为移动到 `_trash` 或 `quarantine`，保留恢复能力。
8. AI/OCR 结果不是事实。按文件哈希缓存识别结果，并把低置信度或歧义项交给
   人工审核。
9. 自动匹配只处理证据充分且结果唯一的记录；不要把最高分等同于可靠匹配。
10. 所有成果必须可通过命令重新生成并验证。

## 第一步：检查现有项目

先读取入口文件、README、配置、数据模型、处理工作流、文件命名、测试和旧版
Excel 生成代码。回答以下问题后再修改：

- 正式数据当前在哪里，哪些字段由程序生成，哪些字段允许人工决定？
- Excel 当前承担事实存储、展示、审核输入还是导出交换？
- 哪些自动结果可信，哪些结果必须进入人工审核？
- 文件是否会移动或重命名，如何验证路径、大小和哈希？
- 页面是否需要调用系统默认程序打开文件，或复制真实文件到系统剪贴板？
- Windows、macOS 和 Linux 的支持范围分别是什么？
- 更新正式数据后，哪些 JSON、HTML、索引或缓存必须同步刷新？

保留与任务无关的既有改动。迁移旧成果前先规划备份、演练和恢复路径。

## 第二步：设计数据与审核契约

将正式数据、待审核数据和展示模型分开。

正式数据至少应表达：

```json
{
  "schema_version": 1,
  "dataset_revision": 12,
  "records": [],
  "unmatched_items": [],
  "recognition_cache": {},
  "changes": [],
  "runs": []
}
```

待审核数据至少应表达：

```json
{
  "source_dataset_revision": 12,
  "pending_reviews": [],
  "unresolved_items": [],
  "processed_reviews": []
}
```

每个审核项包含稳定 ID、源文件哈希、候选记录 ID、匹配证据、置信度、允许的
决定和人工备注。不要只保存表格行号、文件名或页面索引。

保存审核决定时：

1. 检查 `source_dataset_revision` 等于当前正式数据版本。
2. 检查审核项 ID、候选 ID 和文件哈希未被客户端篡改。
3. 检查同一文件或同一业务对象没有冲突决定。
4. 在内存中完成全部业务校验。
5. 执行可恢复的文件操作。
6. 原子保存正式数据并增加版本号。
7. 保存审核历史和运行摘要。
8. 重新生成正式展示页及剩余待审核页。

版本过期时拒绝保存，并明确提示重新加载页面；不要静默覆盖较新的处理结果。

## 第三步：划分自动处理与人工审核

为自动处理建立清晰的准入条件。例如：

- 关键字段全部匹配。
- 只有一个严格候选。
- 文件哈希、业务日期或唯一编号满足约束。
- 置信度达到阈值且与第二候选保持足够差距。

不满足准入条件时：

- 有候选但存在歧义：进入 `pending_reviews`。
- 没有严格候选：进入 `unresolved_items`，不要强行推荐。
- 文件损坏、识别失败或路径失效：显示明确原因并保留可重试状态。

页面同时展示原始识别内容、候选数据和匹配依据，使人工能够判断，而不是只显示
一个分数。

## 第四步：生成适合人工工作的 HTML

先建立与 HTML 无关的展示模型，再由一个纯生成函数输出页面。页面从内嵌 JSON
或本地只读 API 渲染，避免在字符串模板中拼接业务逻辑。

默认提供：

- 汇总统计、状态页签、当前页签搜索和可见记录数。
- 固定表头、稳定排序、清晰的状态颜色和空值显示。
- 审核卡片或表格中的原始值、候选值、差异和证据。
- 明确的保存成功、版本过期、文件失效和服务版本错误提示。
- 打印样式和无 JavaScript 时的基本可读性。

针对 2K 桌面页面：

- 容器宽度限制在视口内，禁止页面级水平滚动。
- 使用百分比列宽或 `table-layout: fixed`，长文本允许换行。
- 合并低价值列；内部 ID、绝对路径和调试字段默认不显示。
- 长表头显式分行，单元格使用 `white-space: pre-line` 或等效方式。
- 将详情放入展开区、提示或独立页签，不要无限压缩核心业务列。
- 在目标分辨率和常见缩放比例下实际截图检查。

右键菜单可提高高频操作效率，但同时提供可发现的按钮或键盘路径，避免把关键
功能仅隐藏在右键操作中。

## 第五步：提供安全的 localhost 桥接服务

浏览器不能可靠完成真实文件剪贴板、系统默认程序打开和本地写回。为这些能力
提供只监听回环地址的轻量服务：

```text
GET  /                         返回 HTML
GET  /api/data                 返回当前审核数据
POST /api/decisions            校验并执行审核决定
POST /api/open-path            用系统默认程序打开文件或目录
POST /api/copy-path            复制真实文件或目录到系统剪贴板
```

按需调整端点，但保持以下安全规则：

- 只绑定 `127.0.0.1` 或 `::1`，不要默认暴露到局域网。
- 限制请求体大小并验证 JSON 类型、枚举值和必填字段。
- 将相对路径解析到资料根目录后执行 containment 检查。
- 不接受客户端提供的任意绝对路径。
- 调用外部程序时传参数数组，不拼接 shell 命令。
- GET 不改变状态；写回、打开和复制使用明确端点。
- 对 HTML 和 JSON 设置 `Cache-Control: no-store`，避免页面版本陈旧。
- 返回适合人工阅读的错误，不向页面泄露堆栈或系统敏感信息。

为服务增加版本标识。启动器优先使用系统分配的空闲端口（端口 `0`），启动后
再打开实际 URL，避免旧进程占用固定端口导致页面连接到过期服务。

## 第六步：实现桌面文件操作

区分三种行为：

- 浏览器预览或下载：适合普通 HTTP 文件链接。
- 系统默认程序打开：通过 `/api/open-path` 调用操作系统。
- 复制真实文件后粘贴到资源管理器/Finder：通过 `/api/copy-path` 写入系统
  文件剪贴板，不是复制路径文字。

跨平台分别实现并测试：

- Windows：使用安全的默认打开 API；文件剪贴板使用系统支持的文件列表格式。
- macOS：使用 `open`；文件剪贴板使用 Finder 可识别的文件 URL/alias 格式。
- Linux：若项目要求支持，使用 `xdg-open` 并选择桌面环境可用的剪贴板方案。

保留浏览器默认 `href` 作为降级路径，但从 localhost 页面点击时拦截并调用
系统打开端点。URL 编码只用于链接；API 应传原始相对路径，避免双重编码。

## 第七步：生成跨平台启动器

Windows 和 macOS 使用独立启动器，不要在一个脚本中混杂两套路径语法。

启动器应：

- 从启动器所在位置或配置解析资料根目录。
- 查找项目入口与 Python，不硬编码另一操作系统的路径。
- 正确处理空格、中文和非 ASCII 路径。
- Windows 设置 UTF-8 终端编码；macOS 使用可执行的 `.command`。
- 启动 localhost 服务、自动选择空闲端口并打开浏览器。
- 在失败时保留可读日志，不静默退出。

允许环境变量覆盖特殊安装路径，但提供无需配置的合理默认查找顺序。

## 第八步：记录日志与审计

终端输出带时间戳的工作描述，不把面向程序的整段 JSON 当作最终运行报告。
至少记录：

- 当前阶段及正在处理的文件。
- 是否调用 AI/OCR，或是否命中哈希缓存。
- 自动分类或匹配的理由。
- 进入人工审核的原因。
- 文件移动、隔离、重新分类和失败结果。
- 本次新增、更新、跳过、纠正和待审核数量。
- 正式数据与生成页面的位置。

正式数据中的 `changes` 保存逐项变更，`runs` 保存每次运行摘要。日志便于当次
操作人员阅读，审计数据用于长期追溯，两者不要互相替代。

## 第九步：迁移 Excel 工作流

先确认 Excel 是否包含唯一数据或尚未处理的人工决定。

迁移顺序：

1. 只读分析工作簿结构和实际使用方式。
2. 把仍属事实的数据导入正式结构化存储。
3. 对文件路径、记录数、关键字段和哈希进行迁移校验。
4. 生成 HTML 并完成人工对照验收。
5. 将旧工作簿移入只读历史目录，不立即删除。
6. 停止在新流程中读取旧工作簿，避免双向同步。

不要长期维护“JSON 改 HTML、人工改 Excel、程序再读 Excel”的循环。

## 第十步：验证

至少覆盖以下自动测试：

- 正式数据到展示模型的字段、状态、排序和缺失值。
- HTML 转义、JSON 内嵌安全和非 ASCII 路径。
- 审核决定的正常保存、非法枚举、冲突和过期版本拒绝。
- 路径越界、文件不存在、哈希变化和重复提交。
- 文件打开与剪贴板函数的 Windows/macOS 分支，测试中模拟系统调用。
- 动态端口启动器和启动命令。
- 数据、文件和 HTML 的一致性校验命令。
- 同一修复命令重复运行不产生额外变更。

进行人工验收：

1. 在目标屏幕尺寸确认无页面级水平滚动。
2. 测试搜索、页签、固定表头、长文本和空数据。
3. 完成一条“待审核 → 保存 → 正式数据更新 → 页面刷新”的闭环。
4. 左键用默认程序打开 Word、PDF 和图片。
5. 右键复制文件并在资源管理器或 Finder 中粘贴。
6. 同时打开旧页面再更新数据，确认过期页面无法覆盖新版本。
7. 重启启动器，确认不会连接到旧后台。

交付前运行项目原有测试、静态检查、编译检查及差异检查。报告自动测试结果、
人工验收范围、数据迁移结果和仍需用户决定的事项。

## 推荐项目结构

按现有项目调整命名，不要求照搬：

```text
entrypoint
src/
├─ repository              # 正式数据读写与原子保存
├─ models/schema           # 数据与审核契约
├─ workflows               # 自动处理和业务状态转换
├─ review                  # 候选、审核决定和回写
├─ review_web              # localhost 服务与桌面桥接
├─ summary_html            # 正式数据 → 展示模型 → HTML
├─ launchers               # Windows/macOS 启动器
└─ validation              # 数据、文件和成果校验
tests/
```

保持模块边界：业务判断不放进 HTML 模板，文件系统操作不放进浏览器脚本，审核
写回不绕过 repository，展示字段调整不改变正式数据语义。
