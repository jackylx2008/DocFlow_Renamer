# 构建可审计的记录归档工作流

## 目标

把零散脚本和文件整理任务设计为可重复、可恢复、可解释的记录工作流。保持三类
对象彼此独立：

```text
业务记录（身份、字段、状态）
    ↕
文件证据（相对路径、角色、哈希、大小、来源）
    ↓
派生成果（HTML、报表、索引、审核清单）
```

不要让目录名代替业务模型，也不要让 Excel、HTML 或文件名同时充当正式数据。

## 参考分层

按项目规模调整模块数量，但保持依赖方向：

```text
统一入口 / CLI / API
        ↓
编排层：选择命令、控制顺序、汇总运行结果
        ↓
领域工作流：归档、去重、匹配、审核、修复、迁移
        ↓
基础能力：repository、命名、哈希、识别、文件操作
        ↓
外部资源：正式数据、文件系统、AI/OCR、旧系统

领域数据 ──→ 成果生成器 ──→ HTML / 报表 / 索引
领域数据 ──→ 独立校验器 ──→ 机器可判定的校验结果
```

让入口只负责编排。不要在 CLI 中实现匹配规则、文件命名或状态判断。让成果生成
器只读正式数据，不反向影响领域工作流。

## 核心不变量

编码时始终保持：

1. 只提供一个对外编排入口；子命令表达不同工作流。
2. 明确代码根目录和资料根目录，所有证据文件限制在资料边界内。
3. 只设一个正式结构化数据源，并给它定义 schema 版本。
4. 二进制文件保留在文件系统；正式数据保存稳定 ID、相对路径、角色、大小、
   哈希和来源。
5. HTML、Excel、缓存和审核清单均为可重建的适配层或暂存层。
6. 文件写操作先校验、后执行、再复核；冲突时停止或隔离，不覆盖未知内容。
7. 重复文件和重复记录默认可恢复处理，不直接删除。
8. 自动匹配只接受证据充分且结果唯一的情况，歧义交给人工。
9. 每次变更记录逐项审计和运行摘要；修复命令必须幂等。
10. 独立校验数据、文件证据和派生成果之间的一致性。

## 第一步：先画出现状关系

读取入口文件、README、配置、模块、数据文件、目录约定、旧成果和测试。列出：

- 业务记录的身份字段和生命周期状态。
- 哪些文件是原始证据，哪些文件由程序派生。
- 现有数据权威：数据库、JSON、Excel、目录名或多个来源。
- 所有会移动、复制、重命名、覆盖或删除文件的代码路径。
- 自动分类、去重、匹配和人工判断的实际规则。
- 旧系统、兼容层、AI/OCR 和外部服务的边界。
- 运行中断后可能出现的半完成状态。

先生成模块关系和数据流，再决定重构结构。不要只按文件名重新分目录。

## 第二步：定义聚合记录

把一个可独立归档、匹配和审核的业务对象作为聚合根。为它定义：

- 稳定 `record_id`。
- 可解释的业务身份键。
- 规范显示名称和证据目录。
- 正式业务字段。
- 当前状态和终止状态。
- 必需证据角色与缺失角色。
- 文件证据集合。
- 外部审批、回执或关联结果。
- 记录级历史。

使用类似结构：

```json
{
  "record_id": "stable-id",
  "record_name": "readable-name",
  "record_directory": "records/readable-name",
  "status": "materials_incomplete",
  "business": {},
  "required_evidence_roles": [],
  "missing_evidence_roles": [],
  "evidence": {},
  "relationships": {},
  "history": []
}
```

根据领域替换字段，不复制示例名称。让状态和缺失项由业务字段及实际证据计算，
不要让展示层自行猜测。

## 第三步：设计正式数据契约

正式数据至少表达：

```json
{
  "schema_version": 1,
  "dataset_revision": 0,
  "data_root": "...",
  "records": [],
  "unmatched_items": [],
  "recognition_cache": {},
  "changes": [],
  "runs": []
}
```

每个文件证据至少保存：

```json
{
  "file_id": "stable-id",
  "role": "source_document",
  "path": "records/example/source.pdf",
  "original_name": "incoming.pdf",
  "current_name": "source.pdf",
  "sha256": "...",
  "size": 12345,
  "derived": false,
  "exists": true
}
```

使用相对路径。绝对资料根目录可以记录用于诊断，但不能成为跨设备识别文件的
唯一方式。

区分版本：

- `schema_version` 表示数据结构兼容性。
- `dataset_revision` 表示正式内容更新次数。
- 规则版本表示匹配、识别或分类算法版本。

不要混用这三类版本。

## 第四步：建立统一入口和命令边界

提供一个入口，并把命令分为：

- 只读：`status`、`validate`、`plan`、`preview`。
- 派生：`export`、`build-review`、`rebuild-index`。
- 变更：`run`、`archive`、`apply-review`、`repair`、`migrate --apply`。

默认命令可以运行常用增量流程，但不要把一次性迁移、破坏性修复或人工决定
隐式塞入日常命令。

入口执行固定编排：

```text
解析配置
→ 校验资料根目录
→ 加载正式数据
→ 调用领域工作流
→ 更新 dataset_revision
→ 追加 run 摘要
→ 原子保存
→ 重建派生成果
→ 输出人类可读日志
```

让工作流返回结构化摘要，不让入口根据日志文本判断是否有变化。

## 第五步：守住目录和文件边界

集中实现：

- `resolve_data_root`
- `ensure_within(path, root)`
- `relative_path(path, root)`
- `sha256_file(path)`
- `atomic_save(data)`

任何来自配置、正式数据、审核页面或用户参数的路径，都要解析后验证仍位于允许
根目录。不要依赖字符串前缀判断路径边界。

根据项目需要设置 `records/`、`trash/`、`quarantine/`、`templates/`、
`legacy/` 等目录。目录名是适配选择，不是方法论强制项。

## 第六步：建立确定性命名和稳定标识

将业务身份与文件显示名称分开：

- 从规范业务字段构造可读记录名。
- 从记录 ID、内容哈希和目标相对路径构造稳定文件 ID。
- 使用明确的角色标签和顺序号命名同类附件。
- 保留原始文件名和当前文件名。
- 保留扩展名语义，不根据未经验证的文本随意改格式。

可使用 UUIDv5 或领域唯一键生成稳定 ID；使用 UUIDv4 表示真正随机的新事件。
不要使用数组下标、Excel 行号或易变的文件名作为唯一标识。

目标已存在时：

- 哈希相同：视为幂等命中或重复证据。
- 哈希不同：停止、生成新名称或进入冲突处理。
- 永远不要静默覆盖。

## 第七步：把文件操作做成可验证事务

文件系统无法与 JSON 自动组成数据库事务。用显式步骤降低半完成风险：

1. 校验源路径位于允许边界。
2. 计算并记录源文件大小和哈希。
3. 计算唯一目标并检查冲突。
4. 创建目标父目录。
5. 移动或复制单个文件。
6. 验证目标存在、大小及哈希一致。
7. 写入正式文件记录和 `changes`。
8. 在长流程中执行 checkpoint。

每项变更记录：

```json
{
  "action": "move",
  "source": "...",
  "target": "...",
  "role": "...",
  "record_id": "...",
  "result": "completed",
  "at": "..."
}
```

设计重跑逻辑：如果目标内容已经正确，记录 `already_exists` 并继续；如果源文件
缺失但目标与计划一致，允许恢复；如果状态不明，停止并要求人工处理。

## 第八步：从业务规则计算状态

把状态刷新写成纯领域函数：

```text
业务字段 → 所需证据角色
实际存在的证据 → 缺失角色
外部回执/审核结果 + 缺失角色 → 当前状态
```

终止、作废、冻结等终态要优先保护，避免日常刷新把它改回活动状态。

检查“实际存在的证据”，不要只看 JSON 数组非空。状态改变后记录原因和时间。
展示层可以产生提示色和辅助核对，但不能偷偷改变正式状态。

## 第九步：治理重复记录

先定义严格业务身份键。只归一化不会改变语义的内容，例如日期格式、空白和明确
等价的标点。身份键缺少关键字段时，不自动判重。

判重流程：

1. 按身份键收集重复组。
2. 计算每条记录的完整度。
3. 选择资料最完整的保留记录。
4. 按哈希把其他记录中的唯一证据合并到保留记录。
5. 将完全重复证据和较少资料的记录移到隔离区。
6. 刷新保留记录状态。
7. 从正式记录集合移除被合并记录。
8. 记录保留理由、合并内容和隔离位置。

完整度使用稳定的字典序评分，而不是难解释的单一权重。例如依次比较：

```text
实际存在的必需证据数
→ 是否已有正式结果
→ 正式结果文件数
→ 已填充证据角色数
→ 唯一文件哈希数
→ 缺失证据数的相反数
→ 是否为原始规范名称
```

让评分函数可单元测试。发生并列时使用明确且稳定的规则。

## 第十步：设计自动匹配

把“候选准入”和“候选排序”分开。

候选准入使用不可妥协的硬条件，例如：

- 关键业务字段同时严格命中。
- 唯一编号一致。
- 文件类型和生命周期状态允许关联。
- 时间范围未违反领域约束。

只对通过准入的候选计算排名。排名可以使用日期差、相似度、来源优先级等软证据。

处理结果：

- 一个严格候选：在业务允许时自动关联。
- 多个严格候选：保留最高项及次高差距，进入人工审核。
- 没有严格候选：进入无候选队列，不强行推荐。

不要因为某项得分最高就自动匹配。记录规则版本、候选数量、每项证据、候选自身
匹配度、第二名和领先差距，使结果可解释。

## 第十一步：把 AI/OCR 作为可替换适配器

优先使用确定性能力：

```text
规范文件名 / 元数据
→ 文件内嵌文本
→ 传统解析
→ 最后才调用 AI/OCR
```

按内容哈希缓存识别结果，包括空结果。缓存至少保存：

- 原始或规范化文本。
- 识别方式。
- 文件名。
- 识别时间。
- 识别规则或模型版本。

延迟启动本地 AI，只在缓存未命中且确定性提取不足时连接。识别完成后尽快
checkpoint，避免后续失败导致重复计算。

分类时识别结构和状态，不只搜索关键词。例如模板包含某选项名称，不代表该选项
已勾选；表头存在不等于表格包含有效记录。把这些判断写成独立、可测试的领域
函数。

## 第十二步：设置人工兜底

使用独立审核暂存数据，但让正式数据保持唯一权威。审核数据至少包含：

```json
{
  "schema_version": 1,
  "source_dataset_revision": 7,
  "rule_version": "match-v2",
  "pending_reviews": [],
  "unresolved_items": [],
  "decisions": []
}
```

使用“证据哈希 + 候选记录 ID”生成稳定审核 ID。保存决定时依次验证：

1. 审核数据对应当前 `dataset_revision`。
2. 审核 ID、证据哈希和候选记录 ID 未变化。
3. 决定属于允许枚举。
4. 同一证据未确认多个记录。
5. 同一记录未被互斥结果重复占用。
6. 证据文件仍存在且哈希未变化。
7. 候选记录仍存在且状态允许。

确认后执行归档并记录人工依据；排除只影响该候选关系；删除决定移动到可恢复
区域。应用成功后增加正式数据版本，重建审核数据和所有派生成果。

## 第十三步：只从正式数据生成成果

让 HTML、Excel、索引和统计报告都遵循：

```text
正式数据 → 展示模型 → 输出文件
```

不要从旧成果反向补正式数据，也不要读取上次 HTML 来判断当前状态。需要人工
输入时使用明确的审核契约和回写服务。

成果生成器应：

- 只读领域数据。
- 对字段排序、标签、颜色和辅助核对集中建模。
- 转义用户内容并安全编码路径。
- 保留生成版本和正式数据版本。
- 可以被 `export` 命令独立重建。

展示提示可以比正式状态更丰富，但要明确哪些是派生判断。

## 第十四步：采用计划式迁移

旧目录或旧工作簿迁移采用两阶段：

```text
扫描旧数据 → 构建完整计划 → 输出 dry-run
→ 人工检查并验证备份 → 执行计划 → 逐项复核
→ 保存正式数据 → 生成成果 → 完整校验
```

迁移计划列出每个 move/copy、源、目标、角色、记录 ID 和预期哈希。执行前对正式
目录和用户备份比较相对路径、大小与哈希；任一差异都停止。

执行每项操作时再次检查：

- 源文件仍存在。
- 源哈希未变化。
- 目标不存在，或目标哈希相同。
- 操作后目标哈希正确。

将旧解析器或旧系统读写封装为兼容层。新入口和新业务规则不要继续堆入兼容模块。
验证稳定后再逐步拆分兼容实现，不要在迁移时同时重写所有成熟解析逻辑。

## 第十五步：为历史数据提供修复命令

规则升级后不要只修复新输入。提供显式 `repair` 或 `reclassify` 命令：

1. 读取已有正式数据和识别缓存。
2. 用新规则重新判断目标范围。
3. 输出或记录将改变的记录。
4. 重新分类存在的证据。
5. 清理确定失效的引用。
6. 刷新状态和派生成果。
7. 记录规则版本、修改数量和无法判断数量。

修复命令必须可重复运行。第二次运行应得到零变更，而不是生成新副本。

## 第十六步：独立校验

让 `validate` 不依赖日常写入流程，并以非零退出码表达失败。至少检查：

- schema 版本受支持。
- 记录 ID、文件 ID 和业务唯一键不冲突。
- 目录及文件路径不越界。
- 证据目录和文件存在。
- 文件大小与哈希一致。
- 必需证据、缺失证据和状态相符。
- 关联结果没有一对多冲突。
- 审核数据版本没有过期。
- 派生成果记录数、页签、链接和正式数据一致。

区分错误与警告。路径越界、哈希不同、ID 冲突属于错误；缺少旧记录的可选元数据
可以是警告。

## 第十七步：记录可读日志和审计

终端日志面向当次操作人员，正式审计面向长期追溯。

日志显示：

- 当前阶段和正在处理的对象。
- 是否使用缓存或外部能力。
- 自动归档、跳过或进入人工审核的原因。
- 本次新增、合并、隔离、匹配、修复和失败数量。
- 正式数据及成果位置。

`changes` 保存逐项文件或记录变更；`runs` 保存一次命令的摘要、开始/完成时间、
规则版本和状态。不要用一整段机器 JSON 代替人类运行日志，也不要只靠日志承担
审计。

## 可选：输入采集与文件路由

只有项目存在统一投放目录、多个文件类型共享入口或不同工作流可能争抢同一文件
时，才增加输入采集/路由适配器。

路由器应只负责：

- 扫描明确范围。
- 计算哈希并识别基础类型。
- 记录分类理由。
- 把文件交给唯一后续工作流。
- 隔离内容重复的输入。

路由器不应负责业务归档、候选匹配或状态更新。

如果上游已经通过 API、数据库、消息队列、固定目录或明确命令提供输入，直接让
领域工作流接收这些输入，不要为了统一形式额外创建 drop zone。

## 测试策略

优先测试纯规则：

- 业务身份键。
- 必需证据与状态计算。
- 确定性命名和稳定 ID。
- 完整度评分和并列规则。
- 候选准入、排序和置信度差距。
- AI/OCR 结构判断。

增加集成测试：

- 计划迁移不会在 dry-run 改文件。
- 备份差异阻止迁移。
- 迁移后文件、哈希和正式记录一致。
- 重复记录保留更完整者并合并唯一证据。
- 唯一候选自动匹配，多候选和无候选进入正确审核队列。
- 人工决定验证版本、ID 和哈希后才能回写。
- 目标冲突不会覆盖文件。
- 中断后重跑和修复命令保持幂等。
- 派生成果和正式数据一致。

模拟 AI、剪贴板、系统打开和外部服务，测试业务边界而不是依赖真实环境。
